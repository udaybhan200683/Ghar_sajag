## Implementation and reproduced defects

The initial production-backed native-owner fixture reproduced both the missing
first publication-head failure and the interrupted empty checkpoint failure
before production changes. Local reproduction logs are
`code/build/gs148_optionA_repro.log` and `gs148_optionA_empty_repro.log`.

`HubRuntime::recover_native_outbox` coordinates the existing stores before the
target attaches its journal backend, reconciles replay fences and enables normal
restore/ingress. The standalone `DurableEventOutbox::recover()` default stays
strict. The optional typed candidate callback proves the approved conjunction:
checkpoint 0 through the existing full decoder, exactly selected authenticated
identity/body 1 and immutable payload, current authenticated enrollment slot,
generation and owner digest, native epoch 1, all eligible NVS checkpoint/report
roots, completion/compaction inventory and matching replay-witness authority.
Recovery leaves published high-water 0 and next physical ordinal 2. It does not
publish, replay, reduce, synchronize to the cloud or issue an ACK.

`RuntimeStateStore::inspect_initial` is read-only and refuses extra selected
identity bytes or intermediate identity banks. The original local minute lives
in that authenticated identity and is reused on retry. `HubDurabilityOwner` checks
all valid fallback checkpoint banks and all authenticated report-bank records;
retired, conflicting, future-epoch or ahead-of-root witness authority refuses.
Existing selector/report pinning and authenticated checkpoint-conflict behavior
are preserved. Damaged ineligible checkpoint banks use ordinary validated fallback
selection rather than acquiring new authority.

Exact authenticated retry re-syncs and decrypts/readbacks the original staged
frame, checks its digest, then uses the ordinary v1 publication, reducer and
application-checkpoint path before Durable ACK. Another key cannot take a
prepared ordinal, including when only identity 1 exists without a complete body.
Conflicting payload or changed enrollment binding is rejected. A lost ACK/reboot
returns the ordinary duplicate Durable result with no duplicate reducer effect.

Three additional source-derived boundaries were reproduced and corrected:

- A pending original could be discarded if Privacy mode changed before retry.
  The already selected, owned native first transaction now completes its original
  admission; current Privacy still suppresses passive interpretation, and fresh
  passive events still receive ordinary policy discard without new identity writes.
- Repeated body-prefix failures could prevent a later complete matching body from
  recovering when publication also failed. Same-ordinal quarantined prefixes are
  not additional transactions or authority. They remain charged to capacity;
  an extra tail beyond the single selected body still fails closed.
- Ordinary recovery could truncate a torn completion tail before checking whether
  missing-checkpoint repair was safe. The coordinator now proves raw body banks,
  completion bytes and publication/lifecycle metadata empty **before** recovery
  cleanup. Two negative cases require unchanged evidence across two boots.

The latter two pre-fix failures are recorded in
`code/build/gs148_optionA_quarantine_repro.log` and
`code/build/gs148_optionA_empty_inventory_repro.log`. The narrow repair completes
only the existing checkpoint-0 object under authenticated native zero-history
ownership. Missing checkpoint plus selected identity/body, malformed checkpoint,
history or any raw inventory is never repaired.

No persistent codec/schema, key derivation, NVS key/namespace, partition, wire
message, enrollment platform, receipt contract or ACK class/path changed.
No production reclamation was enabled. Target startup uses the existing security
link's enrollment resolver; Node production firmware remains unchanged.

## Compatibility, performance and remaining qualification

GS-D033 requires the corrected reader in **both** supported commercial R1 S3
images. This package proves byte-reader compatibility at software level, not an
installed signed pair, actual slot rollback, boot-health integration or physical
OTA qualification. No concrete commercial signed pair is selected here.

Incremental persistent format/authority bytes: zero. Empty recovery completes
the existing checkpoint rather than adding an object type. Pending recovery is
read-only; retry adds one sync plus authenticated readback before ordinary
publication, without re-encrypting an unchanged body. Coordinator contexts are
bounded stack values; it reuses the existing runtime/decoder and bounded indexes.
No new resident cache/reducer, PSRAM reservation or cloud dependency is added.
Production S3 image: **1,878,944 bytes** of 4,194,304-byte OTA slot, 2,315,360
bytes free; **+3,728 bytes** versus the prior 1,875,216-byte baseline image.
GS-114 S3 fixture image: **1,887,440 bytes**, 2,306,864 bytes free; **+3,840**
versus its prior 1,883,600-byte fixture baseline. C3 paired images: production
934,192 bytes, fixture 939,024 bytes. Target `idf.py size` reports static DIRAM
107,761/341,760 bytes, unchanged from the prior production baseline. The Xtensa
owner entry frame remains 30,848 bytes with an unchanged 81,920-byte owner task
allocation; the new zero-history verifier frame is 12,944 bytes. These are
compile-time measurements, not a physical stack high-water result.
Runtime high-water RAM/PSRAM, latency, wear and true power-loss guarantees remain
physical qualification, not inferred performance measurements.
