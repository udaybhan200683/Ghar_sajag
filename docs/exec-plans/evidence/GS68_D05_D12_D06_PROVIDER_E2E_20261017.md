## Implemented

### D05/D12 identity and registry seam

- GS-168 `TestOnlyIssuer` now implements the existing
  `CloudCredentialRegistry.by_fingerprint` structural interface. It returns the
  issuer-owned permanent Hub association, purpose, RSA-3072 algorithm and
  active/revoked/superseded state. Its SQLite operations are serialized for the
  local TLS server thread. It still rejects every non-`TEST_ONLY` environment.
- TEST_ONLY X.509 markers are noncritical so ordinary TLS implementations can
  validate the chain; the issuer and backend continue to require the exact
  marker and registry row. The issuer's private extension is not treated as an
  authentication source.
- The existing backend verifier consumes the registry result after a TLS 1.2
  client-auth chain check, validates certificate dates and RSA-3072/client-auth
  purpose, and joins the permanent Hub ID to current active Home/epoch state.
  Request headers and JSON do not supply identity or authority.
- `ProvisionedS3CloudTrust` validates the injected client certificate as a
  parseable RSA-3072 ClientAuth leaf and checks that its SHA-256 fingerprint
  matches the registry material. It composes identity from one material
  generation and re-reads after trusted-time acquisition; ownership revision,
  certificate generation, binding, or revocation changes fence a mixed
  snapshot.
- A new TEST_ONLY localhost TLS test issues the client certificate through
  GS-168 and sends a GS-40 NodeHealth snapshot through the existing backend API
  and caregiver query projection. It covers live ownership transfer, registry
  revocation, expired credentials, unknown Hub association, ONLINE, silent
  lease expiry to OFFLINE, and stale source to UNKNOWN.

The C++ source interface is still the approved factory/provider boundary. The
host fixture does not claim a physical DS handle, actual hardware key custody,
or that the backend registry is available on the Hub while offline. The backend
revalidates current Home/epoch and credential state for each accepted request.

### D06 signed-time proof

The provider now owns nonce creation and accepts one response for its current
challenge. ESP-IDF builds use `psa_crypto_init()` and `psa_generate_random()`;
host TEST_ONLY tests use OpenSSL `RAND_bytes()`. Failure or an all-zero/reused
nonce prevents readiness. The pinned ESP-IDF 6.0.3 headers/config include
RSA public-key import, RSA PKCS#1 v1.5 signatures, SHA-256, PSA random
generation and NVS `u64` persistence APIs.

Wire proof v1 is a fixed 456-byte envelope. All integers are unsigned
big-endian:

| Bytes | Field |
|---|---|
| 0–3 | ASCII `GSTP` |
| 4 | Version `1` |
| 5 | Suite `1`: RSA-3072 / SHA-256 / PKCS#1 v1.5 |
| 6–7 | Reserved, both zero |
| 8–15 | Current durable boot generation |
| 16–47 | Exact 32-byte one-use provider challenge nonce |
| 48–55 | Signed `issued_at_utc` seconds |
| 56–63 | Signed `valid_from_utc` seconds |
| 64–71 | Signed `valid_until_utc` seconds |
| 72–455 | 384-byte RSA-3072 signature over bytes 0–71 |

The trust anchor is injected as DER SubjectPublicKeyInfo and is independent of
TLS server/client certificate validation. No key or anchor is compiled into
the product. Host TEST_ONLY signing uses a runtime-generated RSA-3072 key; the
target verifier uses the pinned ESP-IDF Mbed TLS RSA/SHA-256 implementation.
The provider enforces one outstanding challenge, nonce and boot-generation
binding, response freshness, interval ordering, maximum signed validity,
monotonic rollback latching, persisted floor comparison, durable floor commit
before readiness, and bounded floor checkpoints. Invalid proof attempts
consume the outstanding challenge. A persisted floor alone does not establish
time after reboot.

`NvsAuthenticatedTimeFloorStore` supplies an ESP-IDF NVS persistence adapter
for an explicitly named namespace. It commits a boot counter and UTC floor and
fails on NVS operation/type/monotonic-write failures. **This is not a
production anti-rollback store:** restoring an older flash image can restore
older NVS values. It cannot replace an approved protected monotonic counter or
sealed store. The target adapter is not instantiated by app composition.

Numeric freshness, statement lifetime and checkpoint/wear policy remain zero
by default and fail closed. The test suite injects TEST_ONLY values only.
Production authority, signing key and trust anchor remain disabled until
owners approve the protocol, storage threat model and numeric thresholds.

## Production approval packet — NOT_YET_APPROVED

For a 50–100 Hub pilot, the simplest secure operational shape is one approved
issuer service using an already-approved managed HSM/KMS-backed signing key,
one trust root, unique short-lived-per-policy Hub leaf certificates, and the
existing GS-165/GS-172 registry interface. Do not introduce a second PKI or
enterprise identity platform. If no approved managed HSM/KMS exists, security
and operations must choose the smallest acceptable custody process before
implementation is enabled. This recommendation is not vendor selection or
authorization.

Approvers must make and record these concrete decisions:

1. **Pilot CA/issuer and root custody (GS-68/security + platform owner):** name
   issuer operator/service and root custody location; select trust-chain
   profile and backend verifier owner; approve backup/recovery, compromise
   response, trust-bundle rotation and access audit. Decide whether the root is
   offline with one HSM-backed issuing intermediate or an approved managed
   private CA. Define a one-operator recovery control.
2. **S3 RSA-3072 DS key custody (GS-68/security + GS-165/factory + hardware):**
   approve the threat model and the exact S3 DS/eFuse-HMAC input-key path;
   define where the key is generated, wrapped, imported, used and destroyed;
   prove it is non-exportable under the selected build/debug/rework policy;
   approve Secure Boot/Flash Encryption interaction, factory station
   isolation, failed-unit replacement and rework. Do not infer protection from
   a pointer or successful build.
3. **Authenticated-time authority (GS-68/security + backend/operations):**
   name the proof signer/operator and protected key location; approve v1 or a
   replacement version, pinned public-key rotation/recovery, endpoint/audience,
   response freshness, signed validity interval, maximum outage behavior and
   boot-generation source. Select the durable protected boot counter/floor and
   checkpoint interval/wear target. Plain SNTP is only a transport hint.
4. **Production registry and certificate lifecycle (GS-165/GS-172 + GS-109 +
   backend):** approve the system of record and its transactional mapping from
   certificate fingerprint to permanent Hub ID, enrollment/source association,
   current Home/epoch, and active/revoked/quarantined state. Set renewal,
   overlap, expiry, revocation propagation, replacement, recovery, audit and
   backend outage rules. The issuer must not infer ownership from a CSR, MAC,
   header or JSON field.
5. **Pilot operations and physical evidence (factory + QA + security):** name
   the issuer operator and recovery approver; approve test-vs-production
   environment separation, negative/revocation fixtures, certificate
   replacement drill, rollback response, source/image evidence and per-fixture
   physical approvals. No real issuance or key operation is requested here.
